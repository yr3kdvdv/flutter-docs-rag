Три вопроса в начале базового прогона Gemini проверяют API и Langfuse. Повтор одного run ID дописывает попытки.

## Последовательность и гипотезы

| Шаг | Фактор | Гипотеза и сравнение |
|---|---|---|
| 1 | Базовый поиск | Gemini section 512, top_k 20, без порога и reranker. Прогон воспроизводит поиск на проверенной версии dev. |
| 2 | Embeddings | Voyage на тех же section 512, с теми же фильтрами и бюджетами. Порядок релевантных секций может измениться между моделями. |
| 3 | Chunking | С Gemini сравнить section 256/512/1024 при overlap 0. При 512 сравнить section, fixed и paragraph. Отдельно сравнить fixed 512 с overlap 0 и 15%. Короткий chunk может точнее выделять факт, длинный может сохранять код и связи. Overlap может сохранить evidence на границе ценой повторов. |
| 4 | Пул поиска | На выбранном индексе запустить фактические `top_k` 3, 5, 10 и 20. Сравнить сырые векторные префиксы и конечные фрагменты. Больший пул может улучшить покрытие. |
| 5 | Порог | Для каждой embedding-модели на section 512, K=20, до rerank, replay порогов 0.35/0.45/0.55/0.65/0.75/0.85 по dev. Разные модели могут требовать разных шкал. Для выбранного индекса повторить проверку при выбранных chunking и K, затем подтвердить выбранный порог реальным прогоном перед включением. |
| 6 | Rerank | Один пул и один порог, одинаковый бюджет. Сравнить Voyage rerank-2.5 on/off по Recall@5, MRR по первым 8 и покрытию контекста. Rerank может поднять evidence при сохранении пула кандидатов. |
| 7 | Генерация | На выбранном поиске сравнить answer/v1.2 с answer/v2 на Gemini Flash-Lite. С выбранным prompt сравнить Gemini и Gemma. Judge — gemini-3.1-flash-lite с judge/v1. Каждый раз меняется один параметр. |
| 8 | Финал | Зафиксировать итоговый конфиг и его SHA до первого запуска на 30 test с `--final`. Финальные результаты описать без ретюнинга. |

Во всех сравнениях максимум 8 фрагментов и 6000 оценочных токенов для ответа,
максимум 1024 выходных токена, temperature 0, дедупликация по content hash, min_chars 80.
Chunking сравнивается по стабильным gold-секциям и документам. Отдельно учитываются
фрагменты, вошедшие в фактический контекст, и размер индекса. Крупный фрагмент
может формально закрыть несколько секций, поэтому Recall сам по себе не гарантирует точность.

## Правила выбора

- Поиск оценивается по section micro Recall@5, Hit@5 в абсолютных числах,
  MRR по первым 8 и покрытию gold-секций в фактическом контексте. Метрики `@K`
  и параметр размера пула `top_k` указываются отдельно.
- Сначала сравнить модели как готовые пакеты на section512. Лучший Gemini chunking
  можно выбрать лишь среди его прогонов. Выбор рабочего индекса делается среди
  действительно измеренных комбинаций. При равном Recall@5 сравнить покрытие контекста,
  MRR@8, затем выбрать меньшее число точек и базовую конфигурацию при прочих равных.
  Модель и размер одновременно не меняются для вывода о влиянии отдельного фактора.
- Выбрать минимальный `top_k`, сохраняющий Hit@5, Recall@5 и покрытие контекста
  относительно K=20. Для порога сохранить эти показатели и все answerable-контексты
  непустыми, повысить число пустых контекстов у unanswerable. При равенстве выбрать
  менее ограничительное значение или `null`, если улучшения нет. Пустой контекст — прокси.
  Проверка отказов выполняется при генерации.
- Включить reranker при улучшении Recall@5 или покрытия контекста с сохранением
  остальных основных показателей. При равенстве оставить его выключенным. Для on/off
  значения за пределами первых 8 не сопоставляются, так как reranker возвращает до 8.
- Для генерации считать долю answerable с данным ответом и оценками correctness
  и faithfulness не ниже 4 из 5, от всех 12 dev с ответом. Ухудшение отказов на трёх
  dev вне корпуса считать регрессией. При равенстве сверить точность цитат, валидные
  источники, код и ресурсы. При сохраняющемся равенстве оставить базовый вариант.
  Judge Gemini может благоприятствовать ответам того же семейства. Добавить отдельную
  качественную сверку выборки с эталонами и выдержками.
- Ошибки API остаются в `raw.jsonl` и считаются отдельно от отказов. При двух ошибках
  подряд остановить очередной прогон и разбирать причину. Ретраи и платный режим
  работают в рамках имеющихся настроек проекта. Явно учитывать попадания в кэш, задержки,
  usage API и оценки токенов, не принимать ноль неподдерживаемого счётчика за расход 0.
- Сравнения описательные. Для 12 вопросов с ответом один вопрос меняет Hit на 8,3 п.п.
  Интерпретация относится к данному корпусу и фиксированному набору.
