# Инструкции ИИ-команде

Выполняй текущую явно назначенную задачу из prompts/. Не запускай все этапы сразу.
Объясняй по-русски. Студент не пишет код вручную; ты создаёшь и запускаешь команды.

Перед работой прочитай docs/PROJECT_BRIEF.md, docs/PROJECT_STATE.md и задание этапа.
Требования сверяй с docs/source/README_PAD.md. Разделяй обязательные требования,
рекомендации методички и наши дополнительные решения. Langfuse обязателен.

Разрешена делегация специализированным субагентам внутри текущего задания.
Начальный предел — два одновременно работающих субагента. Делегируй только
независимые задачи с явными входами, критериями, разрешёнными файлами и выходами.
Пишущие агенты работают в разных Git worktrees после инициализации репозитория.
До появления Git независимые проверки можно делегировать только на чтение.
Главный исполнитель интегрирует работу и отвечает за общий контракт и lockfile.

ChatGPT/текущий Codex-чат — координация; Claude Code — основной исполнитель;
Gemini/Antigravity — независимый аудит; Codex — проверка воспроизводимости.
Субагент Codex не является Claude или Gemini. Указывай фактический инструмент.

Структура skills описана в docs/SKILLS_SPEC.md; сами skills пока не созданы.
При их создании проверь актуальный формат клиента и возможность загрузки.
Не считай файл или название роли доказательством работы агента.

Не публикуй секреты. .env, токены и сырые приватные логи не попадают в Git.
Используй подписочный вход для coding-клиентов; не переключай на платный API
и не включай платные ресурсы без соответствующего решения пользователя.
Доступность моделей приложения подтверждай маленькими реальными API-запросами.
Не меняй провайдера/модель незаметно в эксперименте.

Каждая задача: требования -> реализация -> реальные проверки -> объяснение.
Не выдумывай test pass, metrics, traces, PR или GitHub approvals.
Фиксируй commit SHA, corpus snapshot, dataset version, config и prompt version.
Не допускай утечки эталонных ответов в RAG-корпус или настройки по final test.

Перед публикацией выбери с пользователем аккаунт и видимость репозитория,
если это ещё не указано. Не спрашивай повторно об уже принятом решении.
Внешние сообщения/PR comments публикуй только в рамках явно разрешённого scope.
Сохраняй честную историю: commits и PR по этапам, без имитации прошлой разработки.

В конце обнови docs/PROJECT_STATE.md и docs/handoffs/latest.md по шаблону.
Отчёт: что сделано, что реально проверено, что осталось, доказательства,
объяснение студенту и точный следующий шаг. Ошибки доступа отражай отдельно.

Команд сборки и тестов пока нет. Исполнитель создаёт их на этапе 01 и далее;
до этого нельзя утверждать, что они работают.
